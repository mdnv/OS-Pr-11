# Уровень C — короткие ответы

**1. Страничные отказы на реальной ОС.** `faults.c` запрашивает 64 MiB (`malloc`), затем записывает по байту в каждую страницу. `getrusage(RUSAGE_SELF)` выводит разность `ru_minflt` и `ru_majflt`. На Linux дополнительно читает общие счётчики `minflt` (поле 10) и `majflt` (поле 12) из `/proc/self/stat`. `minor` — без чтения с диска; `major` — с дисковым вводом-выводом. Результаты зависят от ОС. Параметр `volatile` у указателя не даёт оптимизатору выкинуть запись в память.

**2. Пробуксовка / swapping.** Если рабочий набор программы не помещается в RAM, ОС часто выгружает и снова загружает страницы. Повторные проходы замедляются, могут увеличиться `major` faults. В безопасной учебной **Linux VM**, где заранее включён swap и работает cgroup v2, можно запустить `bash level_c/linux_vm_demo.sh`. Скрипт ограничивает память **только для запущенного процесса**, но может вызвать OOM, поэтому не запускать на основном компьютере. Если major faults не выросли, пробуксовка не доказана: наблюдение зависит от окружения.

**3. Локальность 2D массива.** C-массив хранится построчно (row-major). Обход по строкам читает соседние элементы: кэш CPU загружает полезную целую cache line; аппаратная предвыборка работает эффективнее. Обход по столбцам прыгает через длину строки и чаще промахивается мимо кэша. Поэтому `by columns` обычно медленнее, но отношение зависит от CPU/компилятора/размера массива.

**4. Как Linux приближает LRU.** Точный LRU для всех страниц требует дорогостоящего обновления порядка при каждом доступе. В классическом Linux reclaim используются списки `active/inactive` и признаки недавнего обращения: более активно используемые страницы сохраняются дольше. **Multi-Gen LRU** группирует страницы по поколениям (примерной «свежести» обращения), при вытеснении предпочитает старые поколения, учитывая информацию о повторных fault. Это не точная реализация учебного алгоритма LRU; фактическая конфигурация зависит от ядра.

Документация ядра Linux:
- [Multi-Gen LRU](https://docs.kernel.org/mm/multigen_lru.html)
- [cgroup v2: memory.max / memory.swap.max](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- [proc_pid_stat(5)](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html)

**5. Дополнительный вопрос: LRU cache за O(1).** См. `lru_cache.py`: словарь `key -> Node` даёт поиск в среднем за O(1), а двусвязный список позволяет в среднем за O(1) удалить/добавить узел на конец. `get` и `put` — в среднем O(1).


## Проверка swap в Ubuntu VirtualBox (только учебная VM)

```bash
free -h
swapon --show
test -f /sys/fs/cgroup/cgroup.controllers && echo 'cgroup v2 OK'
```

При отсутствии swap опыт с `linux_vm_demo.sh` не запустится (и это ожидаемо). Если преподаватель требует этот опыт, сначала создайте **snapshot VM**, убедитесь, что на виртуальном диске есть как минимум 1 GiB свободного места. Внутри этой VM можно создать временный swap-файл, если нет другого swap:

```bash
sudo fallocate -l 512M /swapfile-pr11
sudo chmod 600 /swapfile-pr11
sudo mkswap /swapfile-pr11
sudo swapon /swapfile-pr11
swapon --show
# после опыта:
sudo swapoff /swapfile-pr11
sudo rm /swapfile-pr11
```

Не добавляйте эту учебную запись в `/etc/fstab`. Эти команды изменяют конфигурацию **только гостевой Ubuntu** и требуют прав администратора; выполняйте их только в VM. Если `fallocate`/`swapon` не сработали (ограничения файловой системы), не форсируйте запуск и попросите разрешённую преподавателем конфигурацию. Эксперимент с памятью возможен только при доступном cgroup v2 и достаточном объёме виртуального диска.
